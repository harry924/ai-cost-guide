How AI model pricing works

A practical guide to what you actually pay for when you use a language model, with interactive examples. It uses Claude's API prices, but the same ideas apply to most model providers.

Paying for Claude Pro or Max, or ChatGPT Plus or Pro, instead? See Subscriptions vs API.

Prices checked from Anthropic's pricing page. Prices change, so check the source before relying on them. Pick a model at the top and every example updates.

Tokens: the unit you pay for

Models read and write text in tokens, which are chunks of a few characters. In English, a token is about 4 characters, or roughly three-quarters of a word. Code, other languages and unusual text use more tokens per character.

Prices are quoted per million tokens, often written MTok. "$4 / MTok" means $4 for every million tokens, or $0.000004 per token.

The same text can be a different number of tokens on different models. Claude models from 4.7 onward use a newer tokenizer that produces about 30% more tokens for the same text than earlier ones. When you compare models, compare the cost of finishing a task, not just the price per token.

Input and output

Every request has two sides, and each has its own price.

  • Input is everything the model reads: the system prompt, the list of tools it can use, the conversation so far, your new message, and the results of any tools it ran, such as files it opened or web pages it fetched.
  • Output is everything the model writes: its reply, any tool calls, and its thinking. Thinking is billed as output even when the app hides it from you.

On every Claude model, output costs 5× as much per token as input. Writing is more expensive because the model generates output one token at a time, while it can read a whole prompt at once.

Tools add input you don't see. The tool definitions are sent with every request, and the API adds a short built-in instruction for tool use (286 tokens on Opus 5.5).

The model has no memory, so every request resends everything

A model doesn't remember anything between requests. To continue a conversation, the app sends the entire conversation again, plus your new message. Message 30 of a chat costs far more than message 1, even if both are one line long, because message 30 carries the 29 exchanges before it.

Prompt caching

When a request finishes, the provider can keep its processed form of that request for a while. If the next request starts with exactly the same content, the model reuses that work instead of processing it again. The app still sends the full text every time; what's saved is the model's work on it, which is why reusing it is so cheap.

This splits input into three prices. Which one a token gets depends on one question: is it already in the cache?

  • Cache read
    Already in the cache, because an earlier request saved it and it hasn't expired.
  • Cache write
    Not in the cache yet: new text, or old text whose cache expired. The model processes it and saves it for next time, which costs more than plain input.
  • Normal input
    Text after the last cache marker, which the app chose not to save.

Some details matter:

  • The match runs from the start. The cache matches the beginning of the request exactly. Change anything early, like the system prompt or the tool list, and everything after the change misses. Adding new messages at the end is fine, which is why conversations cache well.
  • The app chooses what to save by placing a cache marker (cache_control). Coding tools like Claude Code put it at the very end of each request, so they save everything and normal input is close to zero.
  • Entries expire after 5 minutes or 1 hour, depending on which the app asks for. Every read restarts the timer for free, so a cache that's used often never expires.
  • Very short prompts can't be cached. Below a minimum size, caching quietly doesn't happen.
  • Caches are private. They're never shared between organizations.
The most common mistake Your new message is never a cache read, because nothing has saved it yet. With caching turned on it's a cache write. The model's previous reply is also written on your next request: it came back as output, so it wasn't part of anything saved before.

    5-minute or 1-hour cache?

    The two options differ in only one way: what a write costs. A 5-minute write costs 1.25× normal input and a 1-hour write costs 2×. Reads cost the same with either. Which one is cheaper depends on how long you wait between requests.

    Agents that work for hours

    An agent loop sends a new request for every tool call. The model asks for a tool, the tool runs, and its result goes back in the next request. Those requests usually come seconds apart. Each one reads the whole context and restarts the cache timer, so the cache stays warm for hours even though nobody types anything.

    Two things follow from that:

    • Caching is what makes agents affordable. Without it, every step pays full input price to reread the whole context.
    • Reads become the biggest cost. Each read is cheap, but there are hundreds of them and the context keeps growing.

    The cache length matters only for steps with a long wait in between, such as a slow test suite or build, waiting on a sub-agent or background task, or a long generation. The timer counts from the start of a request, so a 4-minute response leaves only 1 minute before a 5-minute cache expires. With a 5-minute cache, each of those waits means rewriting the whole context.

    Because every step rereads the whole context, the best way to cut an agent's cost is to keep its context small: compact it from time to time, and hand reading-heavy work to sub-agents, which do the reading in their own context and pass back only a summary.

    Compaction

    Compaction replaces a long conversation with a summary written by the model. Later requests carry the short summary instead of the full history, so each one costs much less. It has two costs:

    • The compaction itself. The model has to read the whole history once and write the summary as output.
    • Lost detail. A summary can't keep everything. If you later need an exact error message or line of code from early in the conversation, it may be gone.

    Some apps offer to compact when you come back to a long thread after the cache has expired. That's when continuing is most expensive, because the whole history has to be written to the cache again.

    Other things that change the price

    Batch API: half price if you can wait

    Requests sent through the Batch API run in the background instead of immediately, and both input and output cost 50% less. It suits work nobody is waiting on, like classifying a large dataset overnight. The batch discount stacks with prompt caching.

    Fast mode: faster output at a premium

    Fast mode runs the same model with much faster output for double the price: $8 input and $40 output on Opus 5.5. Cache prices scale up with it. It's only available on some Opus models, through Anthropic's own API, and not with the Batch API.

    Long prompts

    Claude 4.6 and later models charge the same per-token rate across the whole 1M-token context window, so a 900k-token request costs the same per token as a 9k one. Claude Haiku 5.5 is the exception: once a request's prompt passes 100,000 tokens, including cached parts, the whole request costs 5× more per token.

    Where the model runs

    Asking for US-only processing (the inference_geo setting) multiplies every price by 1.1. Cloud platforms such as Amazon Bedrock and Google Cloud set their own prices.

    Tools

    • All tools: tool definitions, tool calls and tool results are billed as ordinary input and output tokens.
    • Web search: $10 per 1,000 searches, plus the search results as input tokens. They stay in the context, so later requests read them again.
    • Web fetch: no extra charge beyond the tokens of the fetched page. A typical web page is about 2,500 tokens, and a large PDF can be over 100,000.
    • Code execution: free when used with web search or web fetch. Otherwise each organization gets 1,550 free hours a month, then it's $0.05 per hour per container.

    Subscriptions vs paying per token

    On a subscription plan, such as using Claude Code with a Claude Pro or Max login, you aren't billed per token. Usage counts toward your plan's limits instead. Cost figures shown by the app are estimates at API list prices, which are still a good guide to which requests are heavy. Settings that cost extra, like fast mode, may need extra usage turned on before they actually take effect, so check that a setting applied rather than trusting the menu label.

    Reading the usage numbers

    Every API response reports what it used. These fields map directly onto the prices:

    • input_tokens: normal input, after the last cache marker.
    • cache_creation_input_tokens: cache writes. The cache_creation object splits them into 5-minute and 1-hour writes.
    • cache_read_input_tokens: cache reads.
    • output_tokens: everything the model wrote, including thinking.

    The full prompt size is input_tokens + cache_creation_input_tokens + cache_read_input_tokens. A tiny input_tokens doesn't mean the request was small; the rest came from the cache.

    If cache_read_input_tokens stays at zero across requests that should share a beginning, something early in the request is changing each time, such as a timestamp in the system prompt or a tool list in a different order.

    Ways to spend less

    1. Turn on caching for anything sent more than twice, and keep the start of every request identical: system prompt first, then tools, with no timestamps or random IDs near the top.
    2. Match the cache length to your gaps. Use 5 minutes for steady traffic and fast agent loops, and 1 hour when people pause to read.
    3. Keep the context small. Every token in it is reread on every request. Start new threads for new topics, compact long ones, and use sub-agents for heavy reading.
    4. Pick the smallest model that does the job well, and the lowest effort level that keeps quality. Lower effort means less thinking, and thinking is billed as output.
    5. Use the Batch API for anything that doesn't need an answer right away.
    6. Watch the usage fields. They're the only reliable sign that caching is working.
    7. Judge cost per finished task. A cheaper model that needs three attempts isn't cheaper.

    Glossary

    Token
    A chunk of text, about 4 characters of English. The unit models read, write and bill by.
    MTok
    One million tokens. Prices are quoted per MTok.
    Context
    Everything sent in one request: system prompt, tools, conversation history and the new message.
    Context window
    The most tokens a model can take in one request. 1 million on most current Claude models.
    Input / output
    What the model reads / what it writes. Output costs 5× input on Claude models.
    Thinking
    Reasoning the model does before answering. Billed as output, even when hidden.
    Prompt caching
    Keeping the processed start of a request so the next request that starts the same way costs less.
    Cache marker
    The point in a request (cache_control) up to which the provider saves it.
    Cache write
    Input that isn't cached yet, processed and saved. 1.25× input for 5 minutes, 2× for 1 hour.
    Cache read
    Input that was already cached. 0.1× input on most models, less on some.
    Cache length (TTL)
    How long a cache entry lives without being used: 5 minutes or 1 hour. Every read restarts it.
    Compaction
    Replacing a long history with a model-written summary to make later requests cheaper.
    Batch API
    Requests processed in the background at half price.
    Fast mode
    Faster output on some Opus models at double the price.
    Agent loop
    A run where the model calls tools again and again, one request per step, without waiting for a person.
